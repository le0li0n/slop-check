# ongoing by Tim Bray · Extended Test Drive

*I usually save that title for cars. This time it's about spending five months writing production-ish Go with an agentic coding tool always running in the next terminal window. Herewith field notes: what worked, what didn't, what surprised me, and the rules I ended up with. Short version: it stays, but on a leash.*

## The setup

I don't trust benchmarks-of-the-week or vibes-based takes from people who used one of these things for an afternoon and then wrote a thinkpiece. So I did what I'd do with a car I was thinking of buying: took it out for long enough to stop being on my best behavior.

The vehicle was Quamina, my Go library for matching JSON events against large numbers of patterns. It's a good test case precisely because it isn't a CRUD app. It has a hot loop, a hand-rolled automaton, a data structure that took me a couple of years to get right, and benchmarks I actually care about. It also has a big boring perimeter — parsing, API surface, error handling, tests — of the sort that every real project accumulates.

Five months, part-time. Call it 120 hours at the keyboard. The tool ran agentically: it could read the repo, write files, run `go test`, and iterate on its own failures. I'm deliberately not naming which one, because the specific answer will be stale before this post falls off the front page, and because I don't think it matters much; I sampled two others for a few days each and the shape of the experience was the same.

## Where it just plain won

**Table-driven tests.** Go's testing idiom is a big slice of structs, and writing them is joyless clerical work. The agent is excellent at this. Give it a function and say "table test, cover the boundary conditions, include the UTF-8 nasties," and you get 200 lines that are 90% right in twenty seconds. I'd guess it added a couple hundred test cases to Quamina that I would never have bothered to write by hand, and two of them found real bugs. That alone paid for the exercise.

**Reading unfamiliar code.** I had occasion to go spelunking in a dependency I'd never opened. Asking "where does this allocate?" and getting a guided tour with line numbers, in fifteen seconds, is a genuine superpower. Not because I couldn't do it, but because the activation energy of starting is what usually stops me.

**The stuff between the stuff.** Benchmarking harnesses. A little script to generate a million synthetic events with realistic key distributions. Flag parsing. A GitHub Actions matrix. All of it necessary, none of it interesting, all of it now approximately free.

**Rubber-ducking with a duck that talks back.** I described a data-structure change, it told me the change would break an invariant three files away, and it was right. Not because it's smart, but because it had read all three files more recently than I had.

## Where it drove into the ditch

Here's the part that should worry you.

I asked for an optimization in the matching path. It produced a change that was clean, idiomatic, well-commented, and passed every test in the suite. It also increased allocations per operation by about 40%. The tests didn't catch it because tests check correctness and this was a performance regression, and my benchmarks weren't in the loop the agent was running.

That's the failure mode, and it isn't "the AI writes buggy code." Buggy code is *fine*; buggy code fails loudly and you fix it. The failure mode is **plausible code that satisfies the checks you thought to specify and quietly violates the ones you didn't.** Every experienced engineer carries around a large invisible set of constraints — this path can't allocate, this must stay O(1) in the number of patterns, this API can't change because someone out there depends on it. The agent has no access to that set except through what you type. And you will not think to type all of it.

Second ditch: **correlated errors between code and tests.** When the same process writes the implementation and the tests, a misunderstanding of the requirement produces an implementation and a test that agree with each other and disagree with reality. You get a green checkmark that means nothing. I now think the single most valuable discipline in this whole business is: *the tests for a thing and the thing itself should not come from the same head*, silicon or otherwise. I started writing the test table by hand, then asking for the implementation. Slower. Much better.

Third: it is relentlessly, exhaustingly agreeable. Push back on something it did and it will apologize and change it, whether or not it was wrong. I caught myself twice talking it out of a correct answer. A colleague who never says "no, you're wrong, and here's why" is not a colleague, it's a mirror.

## The thing nobody warns you about

The work changes character. It stops being writing and becomes reviewing.

I like writing code. I do not like reviewing code. Almost nobody likes reviewing code; it's why PRs sit for three days. And this tooling converts a large fraction of your day from the activity people find rewarding into the activity people find draining, while also increasing the raw volume of code arriving at your eyeballs.

There's a real trap here, and I fell into it repeatedly in month two: the code looks *good*. It's formatted, it's commented, it has sensible variable names. Human-written code carries signal about how carefully it was thought through — sloppy naming and a missing error check tell you to look harder. Generated code is uniformly well-groomed regardless of whether the underlying reasoning was sound. It strips out the surface cues that reviewers have unconsciously relied on for fifty years. You have to actually read it, every line, every time, with the same suspicion whether it's a getter or the guts of the automaton. Sustaining that for an hour is hard. For four hours it's not possible, and I stopped pretending otherwise.

## And the flow thing

Programming, when it's going well, is one of the great sustained-attention pleasures available to a person. You hold a structure in your head and you build it. That state is fragile and the tooling is corrosive to it, because every delegation is a context switch: you formulate the request, you wait, you come back, you evaluate. Wait-and-evaluate is a different cognitive mode than build, and oscillating between them at ninety-second intervals is a good way to end a day tired without having thought hard about anything.

I don't want to over-romanticize. Plenty of programming is drudgery and I'm delighted to hand it off. But I noticed that the work I'm proudest of from these five months happened in the sessions where I turned the thing off.

## The rules I ended up with

1. **Tests and implementation never from the same prompt.** Ideally not from the same author.
2. **Benchmarks in the loop, or the loop is lying to you.** If a constraint isn't executable, the agent cannot see it.
3. **Never merge what you haven't read.** If it's too much to read, it was too big an ask. Break it up.
4. **Hot paths and core data structures are mine.** Not out of sentiment — out of the observation above about invisible constraints. That's where they live.
5. **Perimeter work, tests, tooling, exploration: hand it over cheerfully.**
6. **Turn it off for a couple of hours a day.** Partly for the flow. Partly because the skills you don't exercise, you lose, and I'd like to still be able to do this in five years.

## Verdict

I'm keeping it. That's not a grudging concession; on the boring 70% of the work it's a bigger productivity jump than anything since I stopped writing my own build files.

But the marketing story — that this replaces the engineer — is exactly backwards from what I experienced. It makes the easy parts nearly free, which means the *proportion* of your day spent on the genuinely hard parts goes up. Judgment about what to build, knowing which invariants matter, the taste to recognize that a solution is wrong even though it compiles: all more valuable now, not less, because they're the residue that doesn't automate.

That's a good deal for people who have those things. It's a rough deal for anyone who was planning to acquire them by writing a lot of boilerplate first, and I don't know what we do about that.

Test drive over. Buying the car. Keeping both hands on the wheel.
